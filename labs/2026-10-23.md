## Lab 04 — Setting WORKDIR and USER Instructions

**Runbook:** [Lab 04 README](../labs/topic-02-certified-specialist/lab-04-workdir-and-user/README.md)  
**Study guide:** [Lab 04 Deep Dive](../labs/topic-02-certified-specialist/lab-04-workdir-and-user/DEEP-DIVE.md)

### Technical objective

Create a container build that has predictable working-directory behavior and a named non-root process identity. The course example used Red Hat UBI 9 Minimal and separated a root-user WORKDIR baseline from a non-root user configuration.

### Learning outcomes documented

- `WORKDIR /app` determines the starting directory for subsequent build steps and default runtime execution.
- `useradd` establishes an application account; `chown` matters because changing the process user does not automatically grant permission to every filesystem path.
- `USER appuser` changes the default user context for later steps and runtime processes.
- Filesystem ownership, writable directories and Linux user namespaces are different concerns; a container's non-root user is not identical to rootless Podman on the host.
- Verification should use `whoami`, `id`, `podman image inspect`, and targeted writable/denied-path tests rather than relying on configuration alone.

### Evidence and limitations

The archived [course completion image](../labs/topic-02-certified-specialist/lab-04-workdir-and-user/evidence/01-course-platform-completion.png) supports the lesson-completion record. It is **not** a retained transcript proving `whoami`, process identity, or filesystem writes. The Containerfiles in this repository are reconstructed study examples.

**Engineering takeaway:** A secure image needs a deliberate user *and* deliberate filesystem permissions. `USER` alone is not a complete security strategy.

## Lab 05 — Securing Images with Least Privilege

**Runbook:** [Lab 05 README](../labs/topic-02-certified-specialist/lab-05-securing-images-least-privilege/README.md)  
**Study guide:** [Lab 05 Deep Dive](../labs/topic-02-certified-specialist/lab-05-securing-images-least-privilege/DEEP-DIVE.md)

### Technical objective

Build a layered mental model for container image hardening, including vulnerability exposure, cache cleanup, minimal bases, non-root runtime identity, and artifact integrity/provenance.

### Five tasks recorded

| Task | Focus | Main engineering insight |
|---|---|---|
| 01 | Nginx vulnerability scanning | Identify CVEs and affected packages. Use an actual supported scanner such as Trivy rather than assuming `podman scan` is a standard standalone Podman subcommand. |
| 02 | Package cache cleanup | Deleting files in a later image layer does not necessarily remove bytes already embedded in earlier layers. |
| 03 | Alpine/minimal base | Smaller images can reduce unnecessary packages but are not automatically free of vulnerabilities. |
| 04 | Non-root Nginx | A non-root service needs suitable writable paths and an appropriate listening port; document UID and HTTP checks before claiming runtime verification. |
| 05 | Image identity and provenance | Checksums, digests, signatures and trust policies address different questions. An image checksum is **not** a digital signature. |

## Repository discipline and evidence policy

- **Learning records:** Small labs each get a lab-specific `README.md`, `DEEP-DIVE.md`, source/configuration files and only genuine available evidence.
- **Date-wise journal:** Journal entries are grouped by the calendar day, not by arbitrary topics or renamed files.
- **Separate repositories:** AWS projects remain independent from the Domain 5 / Red Hat 1 lab journal.
- **Reproducibility:** Explain intended behavior and show how someone else can verify it; never imply reconstructed commands were captured outputs.
- **Credentials:** Avoid uploading tokens, private keys and account-sensitive information in screenshots or repository files.

## Reflection

A container can start successfully while still being configured with unnecessary privileges or insecure assumptions. Similarly, a GitHub repository can look polished while failing to distinguish implementation details from proof of validation. The engineering standard I want to practice is to explain **what was configured, why it matters, what was tested, and what remains unverified**.
