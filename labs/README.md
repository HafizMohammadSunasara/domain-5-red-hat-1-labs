## Learning objectives

1. Model dependencies using `depends_on`.
2. Start multiple services from a Compose file.
3. Scale the `webapp` service to **three** Nginx replicas and inspect them.
4. Build a Python Flask web app that connects to Redis by its Compose **service name**.
5. Validate connectivity using HTTP and Redis-backed hit counters.
6. Troubleshoot startup, service discovery, published-port conflicts and readiness issues.

## Task 1 — Using `depends_on` directive

### Subtask 1.1 — Create a basic Compose file

Create **`docker-compose.yml`**. The instructor's exact first-stage configuration:

```yaml
version: '3.8'

services:
  redis:
    image: redis:alpine
    ports:
      - "6379:6379"

  webapp:
    image: nginx:alpine
    ports:
      - "8080:80"
    depends_on:
      - redis
```

This exact YAML is saved as [examples/compose-task1.yml](examples/compose-task1.yml). For repeatable reproduction:

```bash
cp examples/compose-task1.yml docker-compose.yml
```

**Security:** The original port mappings bind on host interfaces by default. Only use them in an appropriate isolated training environment; for an RHEL VM/local machine prefer loopback addresses such as `127.0.0.1:6379:6379` and `127.0.0.1:8080:80`, or avoid publishing Redis entirely when unnecessary.

### Subtask 1.2 — Understand `depends_on`

- `webapp` lists `redis` as a startup dependency, so Compose starts Redis **before** Nginx.
- **Started is not the same as ready.** Short-form `depends_on` does **not** guarantee Redis is accepting connections or that an application can use it immediately.
- Here the Nginx image **does not actually access Redis**. Dependency order is being demonstrated; Task 3 adds the actual Redis client.

### Subtask 1.3 — Start services and verify

**Instructor commands:**

```bash
docker-compose up -d
docker-compose ps
```

**Podman alternative:**

```bash
podman-compose up -d
podman-compose ps
podman ps
```

**Expected (not an actual execution log):** One Redis and one Nginx service are running. Image pulls and network creation may occur. Container names are generated by the Compose implementation; avoid treating one naming convention as universal.

**Verification:** Inspect the Compose service list and, if supported, logs using `podman-compose logs` / `docker compose logs` to spot startup problems.

## Task 2 — Scale service replicas

### Subtask 2.1 — Modify Compose YAML

Instructor's second-stage configuration:

```yaml
version: '3.8'

services:
  redis:
    image: redis:alpine
    ports:
      - "6379:6379"

  webapp:
    image: nginx:alpine
    ports:
      - "8080-8082:80"
    depends_on:
      - redis
    deploy:
      replicas: 3
```

Saved unchanged as [examples/compose-task2-scaling.yml](examples/compose-task2-scaling.yml).

```bash
cp examples/compose-task2-scaling.yml docker-compose.yml
```

**Why `8080-8082:80`?** Three replicas cannot all bind host port **8080**. The host port **range** makes it possible for three replicas to receive distinct published host ports where supported. Compose providers can differ in their handling of ranges and `deploy.replicas`. Verify the **actual** bindings with `docker compose ps` or `podman ps`; do not assume a specific replica maps to a particular port.

### Subtask 2.2 — Start scaled services

**Instructor's exact command:**

```bash
docker-compose up -d --scale webapp=3
```

**Modern Docker:** `docker compose up -d --scale webapp=3`  
**Podman (implementation-dependent):** `podman-compose up -d --scale webapp=3`

**Compatibility note:** `deploy.replicas` and `--scale` behavior varies with provider/version. They request **three** replicas here (the values match). If Podman Compose reports an unsupported option, check `podman-compose --help` and use a provider/version implementing Compose scaling, rather than claiming this exact command worked on every installation.

### Subtask 2.3 — Verify scaling and distinct hosts

**Instructor's exact commands:**

```bash
docker-compose ps
docker-compose exec webapp hostname
```

**Expected:** **One Redis** and **three Nginx webapp** containers; each container has its own hostname/container identity. A **single** `exec webapp hostname` checks only one chosen replica, not all three.

**Extra Docker Compose verification (if supported):**

```bash
docker compose ps
# Inspect different replicas instead of repeating the default replica:
docker compose exec --index 1 webapp hostname
docker compose exec --index 2 webapp hostname
docker compose exec --index 3 webapp hostname
```

For Podman, obtain actual container IDs with `podman ps`, then run `podman exec <container-id> hostname` for each. Comparing hostnames is an observation; do not invent outputs or container IDs.

### Subtask 3.1 — Create test application and Dockerfile

**Instructor's complete `app.py`:**

```python
from flask import Flask
import redis
import os

app = Flask(__name__)
redis_host = os.environ.get('REDIS_HOST', 'redis')
redis_client = redis.Redis(host=redis_host, port=6379)

@app.route('/')
def hello():
    count = redis_client.incr('hits')
    return f'Hello World! This page has been viewed {count} times.\n'

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

Unchanged instructor source: [examples/app.instructor.py](examples/app.instructor.py). The runnable [app.py](app.py) included at the lab root preserves the same behavior and adds error handling, short Redis retries and `/health` so failures can be diagnosed without misleading HTTP-500 responses.

**Instructor's complete Dockerfile:**

```dockerfile

WORKDIR /app
COPY . .
RUN pip install flask redis
CMD ["python", "app.py"]
```

Preserved as [examples/Dockerfile.instructor](examples/Dockerfile.instructor). The runnable root [Dockerfile](Dockerfile) uses a supported Python base, [requirements.txt](requirements.txt) and a clean dependency layer for better reproducibility. **Instructor's exact commands:**

```bash

```

**Expected on a fresh Redis key:**

## Troubleshooting — all instructor topics preserved

**Original troubleshooting command:**

```bash
docker-compose logs
```

| Symptom | Likely explanation | What to check/do |
| --- | --- | --- |
| Service doesn't start | Bad YAML, image pull problem, name/port conflict | `docker-compose logs` or `podman-compose logs`, `podman ps -a` |
| Port `8080`, `8081`, `8082`, `5000`, or `6379` is busy | Another container/process has bound the host port | Check `podman ps`, `ss -tulnp`; stop only the conflicting lab service or choose a free port |
| Scaling fails | All replicas require same fixed host port, incompatible range, or Compose-provider limitation | Use distinct host ports/range; inspect actual mapping; check Compose version and `--scale` support |
| Browser works but no Redis counter | Task 1/2 Nginx is not linked to Redis by application code | Execute Task 3 Flask image and final Compose YAML |
| Flask responds 500/503 after startup | Redis not ready / disconnected / failed DNS lookup | Check `REDIS_HOST=redis`, default Compose network, logs, Redis readiness |
| `redis` hostname cannot resolve | Containers not on same Compose network or services named differently | Verify YAML service names and actual network membership |
| `docker-compose: command not found` | Docker Compose v2 generally uses `docker compose` | Use `docker compose`; RHEL Podman path is `podman-compose` if installed |
| Can't see separate replicas | `exec webapp` defaults to one replica | Inspect `ps`; use `docker compose exec --index ...` or actual `podman exec` container IDs |
| Counter changes unexpectedly | Same Redis key persisted/rerun, multiple requests, or another session | Inspect/reset test key **only in disposable lab**; don't assert a fixed count |

## Cleanup — Task 4 from instructor (and stage transitions)

**Instructor's exact cleanup command:**

```bash
docker-compose down
```

**Podman alternative:**

```bash
podman-compose down
```

Run cleanup in the project directory with the desired provider. `down` stops/removes that Compose application's containers and network; it generally **does not delete named volumes by default** and does **not** remove images or source files. Do **not** run global `podman rm -af` just to clean up one lab. Use `docker compose down --remove-orphans` or its supported Podman equivalent only after reviewing unexpected old services.
